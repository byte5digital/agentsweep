# macOS first-run permissions: TCC, Keychain, JIT entitlements and background-item approval

Date: 2026-09-21
Ticket: none named by the requester (feeds `.scratch/ai-antivirus/issues/13-scan-lifecycle-and-daemon.md`, `14-ux-two-postures.md`, `15-distribution-and-release.md`)
Scope: what macOS 14, 15 and 26 will ask the user, or silently deny, when a non-sandboxed, Developer ID signed, notarized Tauri 2 menu bar app (`de.byte5.agentsweep`) registers an in-bundle Rust LaunchAgent (`Contents/MacOS/agentsweepd`, `SMAppService.agent(plistName:)`, `BundleProgram`) that reads, watches and sometimes rewrites coding-agent configuration in the home folder and in arbitrary project folders; plus the CLI, the Keychain, yara-x under the hardened runtime, and background-item approval.

Method: primary sources first (Apple developer documentation and technotes fetched through the documentation JSON API, Apple Platform Security and Deployment guides, WWDC transcripts, Apple DTS answers on developer.apple.com/forums, the yara-x and wasmtime repositories, docs.brew.sh). Every claim carries its source inline. Claims that rest on secondary sources, user bug reports, source reading or inference are marked **UNVERIFIED** in place with what they rest on, and are collected at the end. Nothing here was tested on a signed AgentSweep build; one local read-only check was made on the research machine (macOS 26.6.2) and is labelled as such. Apple states that the list of protected locations "is not documented and ... can change over time", so every TCC statement below is a snapshot. https://developer.apple.com/forums/thread/678819

Section map: 1 TCC scope, 2 attribution for the bundled LaunchAgent, 3 behaviour without consent, 4 detecting and requesting access, 5 CLI attribution, 6 updates and TCC, 7 Keychain, 8 yara-x and the hardened runtime, 9 SMAppService background-item approval, 10 the practical question (ship without Full Disk Access?).

## 1. TCC scope: which paths are protected

**What Apple documents**
- Apple DTS names the mechanism "mandatory access control (MAC)", managed by TCC, and lists its file system privileges by release: Full Disk Access (macOS 10.14+), Files and Folders (10.15+), app bundle protection (13+), app container protection (14+), app group container protection (15+). It adds that the exact list of protected locations is undocumented and changes. https://developer.apple.com/forums/thread/678819
- Apple Platform Security: in macOS 10.15 or later apps need user consent before accessing "files in Documents, Downloads, Desktop, iCloud Drive, and network volumes"; its table lists "Files and folders" as covering Desktop, Documents, Downloads, network volumes and removable volumes. https://support.apple.com/guide/security/controlling-app-access-to-files-secddd1d86a6/web
- The MDM Privacy Preferences Policy Control payload exposes exactly these file services: Desktop Folder, Documents Folder, Downloads Folder, Network Volumes, Removable Volumes, System Policy All Files (Full Disk Access: "data like Mail, Messages, Safari, Home, Time Machine backups, and certain administrative settings"), System Policy Administrator Files. https://support.apple.com/guide/deployment/privacy-preferences-policy-control-payload-dep38df53c2a/web
- Local check on macOS 26.6.2: the Privacy and Security settings extension (`com.apple.settings.PrivacySecurity.extension`) carries the anchors `Privacy_DesktopFolder`, `Privacy_DocumentsFolder`, `Privacy_DownloadsFolder`, `Privacy_NetworkVolume`, `Privacy_RemovableVolume`, `Privacy_FilesAndFolders`, which matches the service list above for macOS 26. Source: `strings` on `/System/Library/ExtensionKit/Extensions/SecurityPrivacyExtension.appex` on the research machine (local observation, not an Apple statement).
- These protections apply to non-sandboxed apps too: Apple DTS diagnoses a non-sandboxed app failing in `~/Documents` with `System Policy: deny(1) file-read-data` as a TCC problem. https://developer.apple.com/forums/thread/663889

**Home-folder dot-directories (`~/.claude`, `~/.claude.json`, `~/.codex`, others)**
- Not in any of Apple's lists above; none of the PPPC services covers the home root or dot-directories. https://support.apple.com/guide/deployment/privacy-preferences-policy-control-payload-dep38df53c2a/web
- **UNVERIFIED** as an explicit Apple statement ("dot-directories are unprotected" is never said in so many words). It rests on the absence from every Apple list and on universal practice (ssh, git, cargo and the coding agents themselves run from unprivileged processes and read these paths without prompts).

**`~/Library/Application Support/<other app>`**
- The macOS 14 "app data" protection covers only data containers: "macOS ensures that they give permission before an app can access data in an application data container from a different developer". Apple tells developers who store data elsewhere (it names "the Library folder") to "adopt App Sandbox in order to extend this new protection", which means a non-container `~/Library/Application Support/<app>` directory written by a non-sandboxed app (Claude Desktop, Codex, VS Code style apps) is not covered. https://developer.apple.com/videos/play/wwdc2023/10053/
- For real containers (`~/Library/Containers/<id>`, and `~/Library/Group Containers/<id>` from macOS 15) the prompt is "X would like to access data from other apps", the grant is "valid for as long as your app remains open, and once the app is quit, the permission resets", same-Team-ID apps are exempt, and "apps ... that have already been granted Full Disk Access" see no prompt. https://developer.apple.com/videos/play/wwdc2023/10053/ , https://developer.apple.com/forums/thread/742147 , https://developer.apple.com/forums/thread/678819
- Consequence: if a future Surface Adapter targets a sandboxed (for example Mac App Store) agent, its config lives in a container, and a long-running daemon without Full Disk Access would prompt once per daemon process lifetime. Apple DTS classes this privilege as "transient, process lifetime". https://developer.apple.com/forums/thread/742147
- Some Apple-owned subdirectories of `~/Library/Application Support` (for example `com.apple.TCC`) are behind Full Disk Access; they are irrelevant to AgentSweep. **UNVERIFIED** from Apple; rests on the Full Disk Access probes used by open-source tools (section 4).

**iCloud Drive and other cloud storage**
- Apple Platform Security lists iCloud Drive among consent-gated locations. https://support.apple.com/guide/security/controlling-app-access-to-files-secddd1d86a6/web
- **UNVERIFIED** detail: the TCC service is reported to be `kTCCServiceFileProviderDomain` (prompt wording "would like to access files managed by <provider>"), covering `~/Library/Mobile Documents` and `~/Library/CloudStorage/*` (third-party File Provider domains such as Google Drive, OneDrive, Dropbox). Rests on user reports, not Apple text. https://github.com/anthropics/claude-code/issues/51911 , https://eclecticlight.co/2025/11/08/explainer-permissions-privacy-and-tcc/
- With "Desktop & Documents Folders" in iCloud enabled, `~/Documents` and `~/Desktop` are still the Documents and Desktop services as far as the path is concerned. **UNVERIFIED**; no Apple source found either way.

**Which grant is needed**

| Location | Protected for a non-sandboxed Developer ID app | Grant |
|---|---|---|
| `~/.claude`, `~/.claude.json`, `~/.codex`, other home dot-dirs, `~/Developer`, `~/code` | No (see UNVERIFIED note above) | None |
| `~/Library/Application Support/<non-sandboxed app>` | No | None |
| `~/Library/Containers/<id>`, `~/Library/Group Containers/<id>` (15+) of another team | Yes, macOS 14+ | Per-process-lifetime prompt, or Full Disk Access |
| `~/Desktop`, `~/Documents`, `~/Downloads` | Yes, 10.15+ | Files and Folders prompt per folder, or Full Disk Access |
| iCloud Drive, third-party cloud storage | Yes | Files and Folders style prompt per provider (UNVERIFIED detail), or Full Disk Access |
| Removable volumes, network volumes | Yes | Files and Folders prompt per class, or Full Disk Access |
| Mail, Messages, Safari, Time Machine, TCC database | Yes | Full Disk Access only |

- Full Disk Access supersedes the per-folder services: if the responsible app has it, no per-folder check or prompt happens. Disabling Full Disk Access does not deny, it only stops granting; switching off a Files and Folders entry is an explicit deny. https://developer.apple.com/videos/play/wwdc2023/10053/ , https://eclecticlight.co/2026/04/08/privacy-files-folders-or-full-disk-access/ (second half **UNVERIFIED**, secondary source)
- Files and Folders is per user; Full Disk Access is system wide. https://developer.apple.com/forums/thread/678819

**Verdict:** Everything AgentSweep needs for the user-level surfaces (`~/.claude`, `~/.claude.json`, `~/.codex`, non-container Application Support) is outside TCC on macOS 14, 15 and 26. TCC only enters through project paths: Desktop, Documents, Downloads, iCloud Drive and other File Provider storage, removable and network volumes. Each of those is reachable with a per-location Files and Folders consent; nothing AgentSweep reads strictly requires Full Disk Access.

## 2. Attribution for the bundled LaunchAgent

- TCC attributes access to "responsible code", not to the process that made the syscall. For a helper inside an app Apple DTS states the intent: the app's name and usage description appear in the alert, the decision is recorded "for the whole app, not that specific helper tool", and it shows up in System Settings under the app's name. The algorithm "is not documented, has changed in the past, and may well change in the future". https://developer.apple.com/forums/thread/678819 , https://developer.apple.com/forums/thread/756510
- For launchd jobs, Quinn (Apple DTS, June 2024): "Run by `launchd` as a daemon or agent: If the daemon or agent was installed by `SMAppService`, that makes the app the responsible code. Otherwise, the daemon or agent should include `AssociatedBundleIdentifiers` in its `launchd` property list." https://developer.apple.com/forums/thread/756510
- Quinn elsewhere gives the same two routes (install with `SMAppService`, or set `AssociatedBundleIdentifiers`) and adds "Or both". https://developer.apple.com/forums/thread/727396
- Does the in-bundle daemon inherit Full Disk Access granted to AgentSweep.app? Kevin Elliott (Apple DTS): "Yes. Part of the reason this API exists is that keeping all of the app components inside the app bundle makes it easier to ensure that TCC permission can be correctly inherited, including FDA", with the caveat that "bugs are always possible, particularly with components executing outside the 'standard' execution flow" and that apps relying on FDA should handle access failures gracefully. https://developer.apple.com/forums/thread/758774?answerId=794648022
- Does a prompt appear for a UI-less background job? "The Files and Folders prompts only show up if the process is running in a GUI login session. If not, the operation is allowed or denied based on existing information. If there's no existing information, the operation is denied by default." A per-user LaunchAgent runs inside the GUI login session (that is what distinguishes an agent from a daemon), so the prompt can appear even though the daemon itself has no UI; tccd draws the alert. https://developer.apple.com/forums/thread/678819 , https://developer.apple.com/library/archive/technotes/tn2083/_index.html
- Prompt text: `"AAA" would like to access files in your Desktop folder.` with AAA being the responsible app, plus that app's usage description. The purpose strings therefore belong in AgentSweep.app's `Info.plist` (`NSDesktopFolderUsageDescription`, `NSDocumentsFolderUsageDescription`, `NSDownloadsFolderUsageDescription`, `NSNetworkVolumesUsageDescription`, `NSRemovableVolumesUsageDescription`), not in the daemon. https://developer.apple.com/forums/thread/678819 , https://developer.apple.com/documentation/bundleresources/information-property-list/nsdocumentsfolderusagedescription
- Difference between an SMAppService `BundleProgram` agent and a legacy `~/Library/LaunchAgents` plist: in-bundle agents "automatically associate with that app"; legacy plists need `AssociatedBundleIdentifiers`, the executable's Team ID must match the app's, and Launch Services must know the app. Without the key, System Settings shows the certificate's organization name instead of the app name. Apple documents this for the Login Items panel; Quinn states the same key drives TCC attribution. https://developer.apple.com/documentation/servicemanagement/updating-helper-executables-from-earlier-versions-of-macos , https://developer.apple.com/forums/thread/678819
- TCC expects a bundled client's `CFBundleExecutable` to be a Mach-O binary, not a script; a Tauri app satisfies this. https://developer.apple.com/forums/thread/678819
- Things that break attribution: a child that daemonises itself (double fork), or an unstable code signature. The daemon must not daemonise; launchd already owns it. https://developer.apple.com/forums/thread/678819
- macOS 26.1 and 26.2 regression: the Full Disk Access and Screen Recording lists showed only apps, and bare command-line executables could not be added with "+" or drag and drop; macOS 26.3 restored the old behaviour. Apple DTS's advice during the regression was to put the daemon inside an app bundle, which AgentSweep already does. The user adds AgentSweep.app, never `agentsweepd`. https://developer.apple.com/forums/thread/806187 , https://developer.apple.com/forums/thread/118508
- **UNVERIFIED** (needs a test on a signed build on 14, 15 and 26): that the first Documents access by an SMAppService agent really produces a prompt naming "AgentSweep" and records the grant under `de.byte5.agentsweep` rather than under the daemon's own signing identifier. It rests on the DTS statements above; a counter-example exists where an in-app-support helper with its own bundle id (`com.anthropic.claude-code`) was the TCC subject instead of the outer app. https://github.com/anthropics/claude-code/issues/93532

**Verdict:** Register through `SMAppService` (already planned), keep the daemon as a plain Mach-O in `Contents/MacOS` signed with the same Team ID, do not give it a separate bundle wrapper or let it daemonise, put all five `NS*UsageDescription` strings in the app's `Info.plist`, and treat "grant to AgentSweep.app covers agentsweepd" as the documented design that still needs one empirical check per macOS major.

## 3. Behaviour without consent

- Error code: "If an operation was blocked by BSD permissions or ACLs, it fails with `EACCES` (Permission denied, 13). If it was blocked by something else, it'll fail with `EPERM` (Operation not permitted, 1)." TCC denials are `EPERM`. In Rust both map to `io::ErrorKind::PermissionDenied`, so inspect `raw_os_error()` to tell them apart. https://developer.apple.com/forums/thread/678819
- Apple DTS also warns that `EPERM` is ambiguous: FDA, data vaults, SIP, sandboxing all produce it, "making it hard to give meaningful guidance to the user". https://developer.apple.com/forums/thread/114452
- Not in a GUI session, or no record and no way to prompt: denied by default, no hang. https://developer.apple.com/forums/thread/678819
- What is enforced is data access, not metadata: the policy denies `file-read-data` (the log line Apple DTS quotes is `System Policy: deny(1) file-read-data`). `open` for reading and directory enumeration count as reading data. https://developer.apple.com/forums/thread/663889
- **UNVERIFIED**: `stat`, `lstat`, `access` and existence checks on a known path inside `~/Documents` succeed without consent and do not trigger the prompt; reading directory contents or file bytes does. Rests on Jeff Johnson's 2020 disclosure and Lily Ballard's comment ("TCC sandbox denies file-read-data ... and does not block anything else (such as metadata)"), not on Apple documentation, and the behaviour may have changed since. https://mjtsai.com/blog/2020/12/07/tcc-doesnt-prevent-protected-folders-from-being-listed/
- **UNVERIFIED**: while the consent alert is on screen, the triggering syscall blocks until the user answers. No Apple statement found; consistent with user reports of tccd servicing a "modal consent prompt". Design for it anyway: never touch a possibly protected path on a thread that serves IPC. https://github.com/randlee/atm-core/issues/1533
- **UNVERIFIED**: denials are cached per responsible process, so a grant made later in System Settings may not take effect until the daemon restarts. Rests on two user reports (macOS 26.5 and 26.6). System Settings itself offers "Quit & Reopen" after a Full Disk Access change for apps, which does not restart a LaunchAgent. Plan to restart `agentsweepd` (or re-probe and then `launchctl kickstart -k`) after the user reports having granted access. https://github.com/randlee/atm-core/issues/1533 , https://github.com/anthropics/claude-code/issues/93532
- Writing: a secondary source states that the per-folder controls do not apply "to writing files". **UNVERIFIED** and not something to rely on; quarantine moves and rewrites need read access first in any case. https://eclecticlight.co/2026/04/08/privacy-files-folders-or-full-disk-access/
- FSEvents: **UNVERIFIED** in both directions. No Apple source says whether an `FSEventStream` rooted in a TCC-protected folder delivers events to a process without consent, and nothing relevant was found in the `notify`, `watchman`, `fswatch` or Syncthing trackers. Even if events arrive, the daemon cannot read the changed file, so the event is useless without the grant. Treat "watch registered, zero events, reads fail with `EPERM`" as the expected failure shape and surface it as a per-project "no access" state.

**Verdict:** Without consent the daemon sees `EPERM` on `open` and `readdir`, not empty listings and not `EACCES`. Probe a project root with one `read_dir` on a worker thread, classify `raw_os_error() == 1` on a TCC-class path as "needs permission" rather than "clean" or "missing", and never let an unreadable project count as scanned.

## 4. Detecting and requesting access

- There is no supported API to query Full Disk Access or a Files and Folders grant. Quinn: "No. I recommend against the approach you're using because the location and permissions of the TCC database is not considered API", and "A better option is to do what you're really trying to do and then handle errors accordingly." Enhancement requests FB6188278 and FB13511819 remain open as of the thread's 2024 posts. https://developer.apple.com/forums/thread/114452
- What tools do in practice (all unsupported heuristics): try to read a file that only Full Disk Access unlocks.
  - MacPaw PermissionsKit probes `~/Library/Safari/CloudTabs.db`, `~/Library/Safari/Bookmarks.plist`, `~/Library/Application Support/com.apple.TCC/TCC.db`, `/Library/Preferences/com.apple.TimeMachine.plist`. https://github.com/MacPaw/PermissionsKit/blob/master/PermissionsKit/Private/FullDiskAccess/MPFullDiskAccessAuthorizer.m
  - `inket/FullDiskAccess` checks readability of `~/Library/Safari` (or `~/Library/Containers/com.apple.stocks` on newer systems). https://github.com/inket/FullDiskAccess/blob/main/Sources/FullDiskAccess/FullDiskAccess.swift
  - A forum participant reads `/Library/Preferences/com.apple.TimeMachine.plist`. https://developer.apple.com/forums/thread/114452
  - These probes target Full-Disk-Access-only locations, so they do not raise a Files and Folders prompt. They do break: a 2026 report says the user TCC database probe no longer works on the macOS 27 beta. **UNVERIFIED** (single user report). https://github.com/bysiber/cleardisk/issues/40
- The probe must run in the process whose attribution matters. Run it in `agentsweepd` and report the result over IPC; a result from the app process only proves the app's own access.
- Files and Folders cannot be queried without risking the prompt: the only test is a real read of the folder, which is the prompt trigger. There is also no API to request it; the first real access is the request. https://developer.apple.com/forums/thread/678819
- Apps cannot be pre-listed under Full Disk Access by an API; the user adds the app with "+" or drag and drop. An app that has attempted a Full-Disk-Access-gated read appears in the list unchecked. **UNVERIFIED** (widely observed, no Apple text found).
- Deep links. Apple documents no `x-apple.systempreferences:` URL for privacy panes; the only supported Settings jump in this area is `SMAppService.openSystemSettingsLoginItems()`. https://developer.apple.com/documentation/servicemanagement/smappservice/opensystemsettingsloginitems()
  - **UNVERIFIED**, community-maintained: `x-apple.systempreferences:com.apple.preference.security?Privacy_AllFiles` (legacy id, used as-is by PermissionsKit and `inket/FullDiskAccess`) and `x-apple.systempreferences:com.apple.settings.PrivacySecurity.extension?Privacy_AllFiles` (macOS 13+ extension id, list extracted from macOS 26.2 binaries by a gist contributor). https://gist.github.com/rmcdongit/f66ff91e0dad78d4d6346a75ded4b751
  - Local check on macOS 26.6.2: the extension bundle id `com.apple.settings.PrivacySecurity.extension` exists, and `Privacy_FilesAndFolders`, `Privacy_DocumentsFolder`, `Privacy_DesktopFolder`, `Privacy_DownloadsFolder` exist as literal anchors. `Privacy_AllFiles` does not appear as a literal string in that binary (it may be composed at run time), so the Full Disk Access anchor on macOS 26 is not confirmed by this check. The URL was not opened during research. Test it on 14, 15 and 26 before shipping, and fall back to opening the Privacy and Security pane without an anchor.
- MDM: managed fleets can pre-grant `SystemPolicyAllFiles` or the folder services to `de.byte5.agentsweep` by bundle id plus code requirement with a PPPC profile, with no prompt. https://support.apple.com/guide/deployment/privacy-preferences-policy-control-payload-dep38df53c2a/web

**Verdict:** No supported check exists. Use "attempt, classify `EPERM`, explain, deep-link" as the primary flow, run any Full Disk Access probe inside the daemon, keep the probe list in one replaceable function, and treat both the probe and the deep-link URL as best-effort conveniences that may break with any macOS release.

## 5. CLI attribution

- Confirmed by Apple DTS: "Run by the user from Terminal: The tool's responsible code is Terminal." Over SSH it is the SSH server (toggle: Sharing > Remote Login > "Allow full disk access for remote users"). Spawned by an app as a helper: the app is responsible. https://developer.apple.com/forums/thread/756510
- The same rule makes iTerm, Ghostty, VS Code's integrated terminal, or the terminal hosting a Claude Code session the responsible code for `agentsweep scan <dir>`. If the CLI is spawned by Claude Desktop's embedded Claude Code, the responsible code is that Anthropic helper. Both follow from Quinn's list; the specific hosts are **UNVERIFIED** individually. Corroboration for "every unsandboxed child inherits the terminal's access": https://lapcatsoftware.com/articles/FullDiskAccess.html
- Consequence: an in-process scan by the CLI succeeds or fails according to the terminal's grants, not AgentSweep's. Developers often have Full Disk Access on their terminal, so the CLI will frequently see more than the daemon does. The signing state of the CLI (in-bundle signed, or unsigned `cargo install`) does not matter for this, because the terminal is the TCC subject.
- CLI talking to the daemon over a Unix socket: TCC evaluates the process that performs the file system call, which is `agentsweepd`, whose responsible code is AgentSweep.app (section 2). The CLI's terminal is irrelevant for those reads. **UNVERIFIED** as an explicit Apple statement; it follows from the responsible-code model, since a socket peer is not a parent, and launchd is explicitly not treated as responsible code. https://developer.apple.com/forums/thread/756510
- Design consequence (inference, not a sourced fact): once the daemon holds Documents access or Full Disk Access, any local process that can reach the socket can ask it to read or rewrite protected paths. The daemon becomes a confused-deputy target, so the socket needs peer checks (peer uid plus, ideally, a code-signature check of the peer via its audit token or pid) and the request vocabulary should stay narrower than "read arbitrary path".

**Verdict:** Correct: CLI file access is attributed to the terminal (or whichever app spawned it). Decide per command whether the CLI scans in-process (terminal's grants, works without the daemon, works for unsigned builds) or delegates to the daemon (AgentSweep's grants); an arbitrary-folder scan is the natural in-process case, and status, quarantine and baseline operations are the natural daemon cases.

## 6. Updates and TCC

- Grants are keyed to the code's designated requirement (DR), not to a hash or a path: "macOS solves this problem by recording your app's DR in its database ... Each time your app tries to access the microphone, macOS checks that this version of the app satisfies the original DR." A Developer ID DR is `anchor apple generic and identifier "<bundle id>" and ... certificate leaf[subject.OU] = <Team ID>`, so version 1.3 replacing 1.2 keeps its grants. https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements
- "Unsigned code has no DR. Ad hoc signed code ... has a DR but it's tied to that specific version of the code. In both cases macOS can't reliably track the identity of the code." Every rebuild re-prompts. https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements
- Apple DTS: "a key factor in TCC validation is your app's designated requirement", and mixing ad hoc and Developer ID builds under one bundle id "seems to break TCC a lot"; use a stable signing identity everywhere, including PR and dev builds (Apple Development signing). https://developer.apple.com/forums/thread/730043
- Pitfalls:
  - Changing the bundle id, the Team ID (company transfer) or the daemon's signing identifier changes the DR and orphans grants. Freeze `de.byte5.agentsweep` and the daemon's `--identifier` before 1.0. https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements
  - Homebrew cask upgrade: "With the uninstall/reinstall strategy, macOS thinks the app is being deleted without any intent to reinstall it, and so it removes some internal metadata for the old app, including ... which permissions it's been granted." Homebrew upgrades in place only when the terminal running `brew` has App Management or Full Disk Access; otherwise it falls back to uninstall and reinstall. Cask users whose terminal lacks App Management can therefore lose AgentSweep's grants on `brew upgrade`. https://docs.brew.sh/FAQ
  - Tauri updater: replaces the `.app` in place. Reports of lost permissions after Tauri updates trace to ad hoc or unsigned builds; the maintainers closed the issue as expected macOS behaviour fixed by signing with a real, constant certificate. No report was found of a Developer ID signed Tauri app losing grants through the updater. **UNVERIFIED** as a positive guarantee. https://github.com/tauri-apps/tauri/issues/10567
  - Versioned install paths are a separate trap: a helper installed under a new `<version>/` directory on each update re-prompted for Documents on every release despite identical bundle id and Team ID. **UNVERIFIED** root cause (user report), but it argues for never relocating `agentsweepd` and never running it from a versioned path outside the bundle. https://github.com/anthropics/claude-code/issues/93532 , https://github.com/anthropics/claude-code/issues/76246
  - Self-modifying bundles are unsupported; anything that invalidates the signature on disk breaks both TCC and Keychain identity. Never write state into the app bundle. https://developer.apple.com/forums/thread/115425
  - The running daemon is the old binary after an update; grants survive, but the app must re-register or kickstart the agent so the new `agentsweepd` runs. (Design note, see `rust-stack.md` section 10.)

**Verdict:** With a constant bundle id, Team ID and signing identifiers, Full Disk Access and Files and Folders grants survive in-place updates by design. The realistic loss path is Homebrew's uninstall and reinstall fallback; document it in the cask caveats and make "permission lost" a recoverable, clearly explained state rather than a silent scan gap.

## 7. Keychain

- macOS has two keychain implementations. The data protection keychain (iOS style, `kSecUseDataProtectionKeychain`) uses keychain access groups, which come from entitlements that "must be authorized by a provisioning profile. Your program needs an app-like bundle structure in which to embed that profile. This is standard for app and app extensions but not for command-line tools." The file-based (login) keychain uses ACLs and needs no entitlement. https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains
- So a Developer ID build without a provisioning profile can only use the file-based login keychain. The data protection keychain is available to a LaunchAgent in principle (it runs in a user context, unlike a launchd daemon, which "must target the file-based keychain"), but only with a profile-authorised `keychain-access-groups` entitlement, and for a bare tool that means wrapping it in its own app-like bundle, which conflicts with the attribution advice in section 2. Whether the app's embedded profile can authorise a second Mach-O in `Contents/MacOS`: **UNVERIFIED**. https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains , https://developer.apple.com/documentation/xcode/signing-a-daemon-with-a-restricted-entitlement
- File-based keychain access control: "items are protected by an access control list (ACL). By default this ACL lists one app, the app that created the item. The ACL references that app using its designated requirement (DR). ... Any code that satisfies this DR can access the keychain. This is what allows keychain access to persist across app updates." https://developer.apple.com/forums/thread/115425
- Updates: same DR (same identifier, same Team ID) means no prompt after an update. A changed DR means the system "treats them as completely separate programs, and hence you get a bunch of authorisation alerts". https://developer.apple.com/forums/thread/654410
- App binary and CLI reading the daemon's item: their DRs differ from the daemon's because the `identifier` term differs (`de.byte5.agentsweep` vs the daemon's and the CLI's identifiers), so by the default ACL each gets the "wants to use your confidential information" alert with Allow / Always Allow. Same Team ID alone is not enough for the file-based keychain. Two ways out: the creator builds a `SecAccess` whose trusted-application array lists all three binaries ("which apps should be allowed to access the item ... without triggering confirmation dialogs"; `nil` trusts "only the calling app"; the API is marked deprecated since macOS 10.10 with "SecKeychain is deprecated"), or, simpler, only the daemon ever touches the item and the app and CLI ask the daemon over IPC. https://developer.apple.com/forums/thread/115425 , https://developer.apple.com/documentation/security/secaccesscreate(_:_:_:)
- **UNVERIFIED**: the file-based keychain additionally stores a "partition list" (`teamid:<TEAMID>` for Developer ID code) and both ACL and partition must match; how the two compose is not publicly documented. Rests on third-party write-ups. https://mostlikelee.com/blog-1/2017/9/16/scripting-the-macos-keychain-partition-ids
- Unsigned or ad hoc `cargo install` CLI: no stable DR (TN3127), so it is never in the ACL; the user gets the password-protected alert, and "Always Allow" is bound to that exact build and breaks on the next rebuild. On Apple silicon `cargo` output is ad hoc signed by the linker, which yields a cdhash-only DR. https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements
- A LaunchAgent can show the keychain alert because it runs in the GUI session; still, a prompt from a background process at login is poor UX and should be designed out. https://developer.apple.com/library/archive/technotes/tn2083/_index.html

**Verdict:** Use the file-based login keychain through `SecItem` from the daemon only, with a frozen signing identifier, and broker every secret read for the app and CLI through the daemon's socket. Do not let an unsigned CLI touch the item. Revisit the data protection keychain only if a provisioning profile is introduced for other reasons.

## 8. yara-x and the hardened runtime

- Current release: yara-x 1.20.0 (2026-08-24), pinned to wasmtime 45.0.3, built with wasmtime features `cranelift` and `runtime`. https://github.com/VirusTotal/yara-x/blob/main/Cargo.toml , https://github.com/VirusTotal/yara-x/blob/main/lib/Cargo.toml
- Apple's entitlements: `com.apple.security.cs.allow-jit` permits writable and executable memory only when it is created "using the `MAP_JIT` flag"; `com.apple.security.cs.allow-unsigned-executable-memory` permits it "without the restrictions imposed by using the `MAP_JIT` flag" and "exposes your app to common vulnerabilities in memory-unsafe code languages". https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.allow-jit , https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.allow-unsigned-executable-memory
- wasmtime does not use `MAP_JIT`. Issue #11989 "Support mmap flag MAP_JIT for MACOS" is still open (last activity 2026-08-20); `crates/wasmtime/src/runtime/vm/sys/unix/mmap.rs` on main maps with `PRIVATE` (plus `NORESERVE`) only and later `mprotect`s the text range to executable. A maintainer reproduced the hardened-runtime kill and confirmed an experimental `MAP_JIT` patch fixes it, but it has not landed; maintainers say it "isn't a high priority" and nobody should "rely on this happening by itself anytime soon". https://github.com/bytecodealliance/wasmtime/issues/11989 , https://github.com/bytecodealliance/wasmtime/blob/main/crates/wasmtime/src/runtime/vm/sys/unix/mmap.rs
- Therefore `allow-jit` alone does not suffice today. A yara-x user with a signed, notarized Rust CLI reports: "`com.apple.security.cs.allow-unsigned-executable-memory` was required, JIT was not enough." A wasmtime embedder (Rama) ships with `allow-unsigned-executable-memory` for the same reason. https://github.com/VirusTotal/yara-x/issues/645 , https://github.com/bytecodealliance/wasmtime/issues/11989
- Failure mode without the entitlement: `SIGKILL (Code Signature Invalid)`, `Namespace CODESIGNING, Code 0x2 (Invalid Page)` on the first scan (rule compilation succeeds). The reporter saw it on macOS 26 and states it did not crash on macOS 13 to 15. **UNVERIFIED** (single user report; the claim that macOS 26 tightened enforcement is the reporter's analysis, not Apple's). https://github.com/VirusTotal/yara-x/issues/645
- The no-JIT option: cargo feature `pulley` on the `yara-x` crate, exact definition `pulley = ["wasmtime/pulley"]`, also re-exported by `yara-x-cli` and `yara-x-capi`. It was added by the commit that closed #645 (2026-05-04) and first shipped in v1.16.0; it is not a default feature. With it, yara-x sets `config.target("pulley64")` (or `pulley32`), so Cranelift emits Pulley bytecode that wasmtime interprets. The feature comment says it "eliminates JIT memory constraints". https://github.com/VirusTotal/yara-x/commit/f9710964beea6d90444955a233518f2ec5fcfb1b , https://github.com/VirusTotal/yara-x/blob/main/lib/Cargo.toml
- Why Pulley needs no entitlement: wasmtime only calls `make_executable` on a module's text when `needs_executable` is true, and Pulley text sections carry `SH_WASMTIME_NOT_EXECUTED`, which sets it to false. No executable pages are created. (Source reading, not a documentation statement.) https://github.com/bytecodealliance/wasmtime/blob/main/crates/wasmtime/src/runtime/code_memory.rs
- Performance cost: wasmtime's documentation says to "expect a ~10x order-of-magnitude slowdown relative to native code or Cranelift". yara-x documents no figure; the #645 reporter measured roughly 3x slower on two benchmarks with estimated baselines (**UNVERIFIED**). Only rule conditions run in WASM; pattern search (Aho-Corasick atoms, regex VMs) is native Rust either way, so the end-to-end cost on small text files depends on how condition-heavy the rules are (inference from the architecture; measure with the v1 rule corpus). https://docs.wasmtime.dev/examples-pulley.html , https://github.com/VirusTotal/yara-x/issues/645
- Precompiling and serialising:
  - `Rules::serialize` / `deserialize` exist. By default the serialised form contains the WASM module, not native code, and `deserialize` rebuilds the module with `Module::from_binary` on the user's machine, which is a JIT compile into executable memory unless `pulley` is on. https://github.com/VirusTotal/yara-x/blob/main/lib/src/compiler/rules.rs
  - The `native-code-serialization` feature (off by default) embeds host-native code: it "reduces the load time ... If rules that were serialized with native code for one platform are deserialized in a different platform, the native code ... is ignored and generated again". https://github.com/VirusTotal/yara-x/blob/main/lib/Cargo.toml
  - Loading precompiled native code does not avoid the entitlement. The deserialised image goes through the same `CodeMemory::publish` path that flips the text range to executable on non-`MAP_JIT` memory, which is exactly what the hardened runtime kills. wasmtime's precompiled-module workflow (`*.cwasm`) removes the compiler, not the need for executable memory. (Source reading plus issue #11989; **UNVERIFIED** by test.) https://github.com/bytecodealliance/wasmtime/blob/main/crates/wasmtime/src/runtime/code_memory.rs , https://docs.wasmtime.dev/examples-minimal.html
  - It also needs per-architecture artifacts (arm64 and x86_64) and `Module::deserialize` is `unsafe` because a tampered blob is arbitrary code execution, which is a bad trade for a security tool whose rule files are user-writable. https://docs.rs/wasmtime/latest/wasmtime/struct.Module.html
  - With `pulley`, serialised rules are portable bytecode; combining `pulley` with `native-code-serialization` to skip compilation at load was not examined. **UNVERIFIED**.
- Entitlements are per executable: only the binaries that link yara-x (`agentsweepd`, the CLI) would need an exception, not the Tauri app binary. The Tauri main binary needs its own review because WKWebView's JIT runs out of process. (General code signing behaviour; see `rust-stack.md` section 11.)

**Verdict:** Build yara-x with `features = ["pulley"]` for every macOS release artifact (daemon and CLI) and ship with no JIT entitlement at all. This supersedes the `allow-jit` plan noted in `rust-stack.md` (section 11 and its unverified item 5): `allow-jit` alone does not work with wasmtime 45, and the entitlement that does work, `allow-unsigned-executable-memory`, is the wrong thing for a security tool to carry. Benchmark the v1 rule corpus under Pulley before committing; if the cost is unacceptable, the fallback is `allow-unsigned-executable-memory` on the daemon and CLI only, revisited when wasmtime #11989 lands.

## 9. SMAppService background-item approval and first run

- `register()` for a LaunchAgent: "the LaunchAgent is immediately bootstrapped and may begin running", and bootstraps again on each login. It is per user; call it once per user. LaunchDaemons, by contrast, wait for admin approval. If the user has disabled the item, `register()` fails with `kSMErrorLaunchDeniedByUser` and `status` is `.requiresApproval`. https://developer.apple.com/documentation/servicemanagement/smappservice/register() , https://developer.apple.com/documentation/servicemanagement/smappservice/status-swift.enum/requiresapproval
- User-visible flow on macOS 13 and later, including 14 and 15: a notification, not a blocking prompt. WWDC22: "Your app will be allowed to launch at login by default, and users will be notified. If your app requires a daemon with elevated permissions, it will require admin approval to enable." "Clicking on the notification opens the Login Items pane in System Settings." "Call the SMAppService API from your app to control when people get the notification." https://developer.apple.com/videos/play/wwdc2022/10096/
- The user can switch the item off later in System Settings > General > Login Items (renamed "Login Items & Extensions" in macOS 15; name **UNVERIFIED**, carried over from `rust-stack.md`). The app should check `status` at launch, explain, and call `openSystemSettingsLoginItems()`. In-bundle agents are listed under the app's name automatically. https://developer.apple.com/documentation/servicemanagement/updating-helper-executables-from-earlier-versions-of-macos
- Exact notification wording ("Background Items Added", "<App> added items that can run in the background. You can manage this in Login Items Settings."): **UNVERIFIED**; no Apple page quoting it was found. For legacy plists without `AssociatedBundleIdentifiers` the notification and Settings row name the certificate organization ("Software from <Org>"), per Apple's doc and a 2026 user report. https://developer.apple.com/documentation/servicemanagement/updating-helper-executables-from-earlier-versions-of-macos , https://github.com/robinebers/openusage/issues/607
- Known rough edges (developer reports, macOS 13.1 era): dismissed daemon notifications that never reappear, stale Login Items rows after app deletion. Apple DTS suspected a regression. Agents were reported to register and unregister without trouble. https://developer.apple.com/forums/thread/721919
- macOS 26 change: "On Mac computers with macOS 26 or later, if background tasks are started by an app and remain active after a user quits the app, the user is prompted to allow or not allow the background tasks to remain active." MDM can suppress it with a Service Management profile keyed on bundle id, bundle id prefix or Team ID. https://support.apple.com/guide/deployment/manage-login-items-background-tasks-mac-depdca572563/web
  - This applies directly to AgentSweep: quitting the menu bar app leaves `agentsweepd` running by design. Expect an allow / don't allow prompt on macOS 26 the first time that happens.
  - **UNVERIFIED**: the exact wording and timing of that prompt, whether it appears once or repeats, whether it fires for an SMAppService-registered agent that the user was already notified about, and what "not allow" does (kill once, or disable the login item so `status` becomes `.requiresApproval`). Apple's one sentence is the only primary text found. Needs a test on macOS 26.
- First-run ordering consequence: call `register()` from an explicit onboarding step ("Turn on background protection") so the notification has context, and show the TCC explanation in the same flow before the daemon first touches a protected project path, since that touch is what raises the Files and Folders alert (section 2).

**Verdict:** On macOS 14 and 15 registration is non-blocking: the agent starts immediately and the user only gets a notification. On macOS 26 add one more expected interruption, the "keep running after quit" prompt. Treat `.requiresApproval`, `kSMErrorLaunchDeniedByUser` and "daemon not reachable" as first-class states in the menu bar UI, and tell the user in onboarding that protection continues after the app quits, so the macOS 26 prompt is not a surprise.

## 10. The practical question: can AgentSweep ship without asking for Full Disk Access?

- Yes. Nothing in the v1 surface list strictly requires Full Disk Access: the user-level surfaces are outside TCC (section 1) and every protected project location can be unlocked by a per-location Files and Folders consent attributed to AgentSweep.app (section 2).
- What happens for a user with projects in `~/Documents`, `~/Desktop`, `~/Downloads`, iCloud Drive or on external and network volumes if nothing is done:
  - The first daemon read of such a project raises a system alert naming AgentSweep, at an arbitrary moment (login, a background scan), once per location class: up to three folder prompts, one per File Provider domain, one for removable and one for network volumes (sections 1 and 2).
  - If the user clicks "Don't Allow", or the alert cannot be shown, every read in that tree fails with `EPERM`; the project's `.claude/`, `.mcp.json`, `CLAUDE.md`, `.codex/`, `.git/config` and hooks go unscanned, watches on them are useless, quarantine and rewrite fail, and there is no second prompt; recovery is manual in System Settings > Privacy & Security > Files and Folders (section 3).
  - User-level surfaces and projects under `~/Developer`, `~/code` and similar keep working.
  - The CLI run from a terminal keeps working for those folders if the terminal has access, which can make CLI and daemon results disagree (section 5).
- What Full Disk Access buys: one deliberate step instead of several surprise alerts, coverage of sandboxed agents' containers without per-launch prompts (section 1), and no per-provider cloud prompts. What it costs: a manual trip to System Settings with no API to request it, a much larger blast radius for the socket (section 5), and a harder story for a security tool.
- Recommended shape: ship without requiring Full Disk Access; make project access an explicit, explained step. When a registry yields a project under a TCC-class path, mark it "needs access", and trigger the first read from a user click in the app so the system alert appears in context. Offer Full Disk Access as an optional "cover everything" setting with a deep link and a daemon-side probe (section 4). Never report an unreadable project as clean.

**Verdict:** Ship without Full Disk Access. The cost is a handful of contextual per-folder prompts and one mandatory UI state ("project not readable: permission needed") with a restart-the-daemon recovery path. The one thing that must not ship is silent degradation, where `EPERM` on a protected project is swallowed and the project shows as scanned.
