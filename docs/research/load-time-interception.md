# Load-time interception via agent hooks

Answers `.scratch/agentsweep/issues/20-load-time-interception.md`. Question: can AgentSweep block a flagged Item before an Agent uses it by registering its own hook with the Agent, and if so at which events, with what blocking mechanics, what the handler sees, what the latency limits are, where the hook must live, whether the Agents' trust gates it, whether the hook entry trips AgentSweep's own Drift rules, and how the handler works under the ticket 13 process model.

## 1. What runs before any hook can fire

The question distinguishes blocking the *loading* of an Item (instruction file read, skill catalogued, MCP server process spawned, plugin components registered, settings applied) from blocking its *use* (a skill invoked, an MCP tool called, a shell command run). The startup order decides which of the two a hook can reach.

| Agent | Loaded or executed before the first hook event | Source |
|---|---|---|
| Claude Code | Settings files of every scope are merged and applied (`env`, `apiKeyHelper` and the other helper commands, `statusLine`, `disableAllHooks`); skill and command directories are scanned ("skill discovery normally runs before SessionStart hooks finish"); MCP servers are being started ("`SessionStart` fires before the servers are available"); `@`-referenced files are inserted without any tool call. Only then does `SessionStart` fire, and it cannot block anything. | `hooks#sessionstart-decision-control` (reloadSkills note), `hooks#mcp-tool-hook-fields` ("At launch" bullet), `hooks#pretooluse` warning on `@` references, `hooks#exit-code-2-behavior-per-event` |
| Codex | Config layers merged; MCP runtime installed with `McpStartupPolicy::Eager` for main sessions; the SessionStart source is only *queued* at session configure and the hooks run inside the first `run_turn`, after pre-sampling compaction, after `build_skills_and_plugins` has read the `$mentioned` `SKILL.md` bodies from disk, and before `UserPromptSubmit`. AGENTS.md is assembled at session start independently of hooks. | `codex-rs/core/src/session/session.rs:1854-1893`, `codex-rs/core/src/session/mcp_runtime.rs:358-362`, `codex-rs/core/src/session/turn.rs:308-322,366-375`, `codex-rs/core/src/hook_runtime.rs:126-175` |

Verdict: neither Agent has an event that fires before instruction files, skills, plugins, settings or MCP server processes are loaded. Every Surface AgentSweep scans is on disk and in memory, and every executable settings key has already run, by the time the earliest hook fires. Load-time blocking is therefore not available; what remains is use-time blocking, examined per Agent below.

## 2. Claude Code

### 2.1 Events that fire before an Item is used

Of the 33 documented events, these are the ones that sit between "session exists" and "flagged content acts". Latency figures are the documented defaults; every `command`/`http`/`mcp_tool` hook may set `timeout` per entry.

| Event | Fires | Can block? | What a block stops | Default timeout | On timeout | Source |
|---|---|---|---|---|---|---|
| `SessionStart` | Session start, resume, `/clear`, compact, fork; runs in the background while the user can already type, but Claude's first response waits for it | No. Exit 2 shows stderr to the user and the session proceeds; JSON is "context only" (`additionalContext`, `initialUserMessage`, `sessionTitle`, `watchPaths`, `reloadSkills`) | nothing | 600 s | output discarded | `hooks#sessionstart`, `hooks#exit-code-2-behavior-per-event`, `hooks#decision-control` |
| `Setup` | Only with `--init-only`, or `--init`/`--maintenance` under `-p` | No; all JSON discarded | nothing | 600 s | — | `hooks#setup-decision-control` |
| `InstructionsLoaded` | When a `CLAUDE.md` or `.claude/rules/*.md` is loaded (session start, nested traversal, `paths:` glob, `include`, compact); async, observability only | No; exit code ignored, JSON discarded | nothing (the file is already in context) | 600 s | — | `hooks#instructionsloaded-decision-control` |
| `UserPromptSubmit` | Every prompt, before Claude processes it | Yes: `decision: "block"` + `reason`, or exit 2 with stderr. The prompt is erased from context | the whole turn: no model request, no tool calls, no skill expansion by the model | 30 s (lowered from 600) | prompt proceeds without the hook's context (fails open); an Agent SDK callback hook is the one hook type that fails closed here | `hooks#userpromptsubmit`, `hooks#timeouts` |
| `UserPromptExpansion` | When a user-typed `/command` (skill, custom command, MCP prompt) expands into a prompt | Yes: `decision: "block"` or exit 2 blocks the expansion | the skill or command body reaching Claude on the direct `/name` path, which `PreToolUse` does not see | 600 s | output discarded, expansion proceeds | `hooks#userpromptexpansion` |
| `PreToolUse` | Before every tool call, including `Skill`, `Agent`, `Bash`, `Read`, `Write`/`Edit` and `mcp__<server>__<tool>`; before permission rules and in every permission mode including `bypassPermissions` | Yes: `hookSpecificOutput.permissionDecision: "deny"` (precedence `deny > defer > ask > allow`) or exit 2. Deny and ask rules still apply on top; a hook cannot loosen them | that one tool call | 600 s | tool call continues through the normal permission flow (fails open); only an Agent SDK callback hook blocks on timeout | `hooks#pretooluse-decision-control`, `hooks#timeouts`, `hooks-guide#hooks-and-permission-modes`, `permissions#extend-permissions-with-hooks` |
| `PermissionRequest` | Only when Claude Code is about to prompt the user (or would auto-deny where no prompt exists) | Yes, but only through `hookSpecificOutput.decision.behavior: "deny"`; exit 2 is not honoured and stderr is discarded | that one tool call | 600 s | flow unchanged | `hooks#permissionrequest-decision-control`, `hooks#exit-code-2-behavior-per-event` |
| `ConfigChange` | A settings file, managed policy file or `.claude/skills/` file changes during a session; input carries `source` and `file_path` | Yes: `decision: "block"` or exit 2, except for `policy_settings`. No message is shown to user or Claude | the changed configuration taking effect in the running session (not the write itself) | 600 s | change applies | `hooks#configchange-decision-control` |
| `CwdChanged`, `DirectoryAdded`, `FileChanged` | `cd` in the main conversation; `/add-dir` or SDK `register_repo_root`; a watched file changed on disk | No | nothing; `DirectoryAdded` runs after the directory is already added and Claude Code does not wait for it | 600 s | — | `hooks#cwdchanged-output`, `hooks#directoryadded`, `hooks#filechanged-output` |
| `SubagentStart` | A subagent is spawned | No; context injection only | nothing | 600 s | — | `hooks#subagentstart` |

The universal `continue: false` field ("Claude stops processing entirely after the hook runs") is accepted on every event but the reference lists the events that discard it; `SessionStart` is not listed among them. The decision-control table nevertheless classifies `SessionStart` as "Context only" with "No blocking or decision control" (`hooks#decision-control`), and the per-event exit-code table says exit 2 only shows stderr to the user, so even if `continue: false` were honoured it would stop Claude after the session's Surfaces have loaded, not before. See section 7.

Async hooks (`async: true`) never block: "response fields like `decision`, `permissionDecision`, and `continue` have no effect" (`hooks#run-hooks-in-the-background`).

### 2.2 What the handler sees

Every command hook receives one JSON object on stdin with `session_id`, `transcript_path`, `cwd`, `permission_mode`, `hook_event_name` and, since v2.1.257, `scratchpad_dir`; the environment also carries `CLAUDE_PROJECT_DIR` (the project root where the session started; `cwd` follows Claude into worktrees and after `cd`), plus `CLAUDE_PLUGIN_ROOT`/`CLAUDE_PLUGIN_DATA` for plugin hooks (`hooks#common-input-fields`, `hooks#reference-scripts-by-path`).

| Event | Item-naming fields | Source |
|---|---|---|
| `UserPromptSubmit` | `prompt` only; the project is identified through `cwd` / `CLAUDE_PROJECT_DIR` | `hooks#userpromptsubmit-input` |
| `UserPromptExpansion` | `expansion_type` (`slash_command` or `mcp_prompt`), `command_name`, `command_args`, `command_source` (for example `plugin`), `prompt` | `hooks#userpromptexpansion-input` |
| `PreToolUse` / `PermissionRequest` | `tool_name`, `tool_input`, `tool_use_id` (not on PermissionRequest). File tools deliver an absolute `tool_input.file_path`. MCP tools deliver `mcp_server: {name, source}` where `source` is `plugin`, `sdk`, `user`, `project`, ...; the docs say to base trust on `source`, not on the name (requires v2.1.274). The matcher takes the tool name; the `if` field takes permission-rule syntax such as `Skill(deploy *)` or `Edit(**/.claude/**)` | `hooks#pretooluse-input`, `hooks#match-mcp-tools`, `hooks#common-fields`, `skills#restrict-claudes-skill-access` |
| `ConfigChange` | `source` (`user_settings`, `project_settings`, `local_settings`, `policy_settings`, `skills`) and `file_path` | `hooks#configchange-input` |
| `InstructionsLoaded` | `file_path`, `memory_type` (`User`/`Project`/`Local`/`Managed`), `load_reason`, `trigger_file_path`, `parent_file_path` (observability only) | `hooks#instructionsloaded-input` |

The `Skill` tool's `tool_input` shape is not listed in the reference's per-tool table (Bash, PowerShell, Write, Edit, Read, Glob, Grep, WebFetch, WebSearch, Agent, AskUserQuestion, ExitPlanMode). The running Claude Code binary exposes the tool with parameters `skill` and `args`, so a hook can expect `tool_input.skill`; treated as observed, not documented (section 7).

### 2.3 Where the hook must live and what gates it

- Scope: `~/.claude/settings.json` hooks apply to "all your projects"; hook entries merge across scopes and no lower scope can remove a managed hook. Edits to settings files are picked up live by the file watcher (`hooks#hook-locations`, `settings#when-edits-take-effect`: "Claude Code watches your settings files and reloads them when they change").
- Trust, interactive sessions: Claude Code "holds back hooks from every settings file, including your own `~/.claude/settings.json`, until you accept the workspace trust dialog for the folder, or for a parent directory whose trust extends to it". So in a never-trusted folder the user hook does not run until the dialog is accepted; after acceptance it runs like anywhere else (`hooks#workspace-trust`).
- Trust, `-p`/SDK sessions: no dialog, the folder counts as trusted, all settings-file hooks run, including a repository's own `.claude/settings.json` hooks (`hooks#workspace-trust`, `permissions#what-runs-before-you-trust-a-folder`).
- Kill switches a repository controls: `disableAllHooks` is a scalar taken from the highest-precedence file, and a project's `.claude/settings.json` outranks user settings, so a repository can set `"disableAllHooks": true` and switch off the user's hooks in that project; only `--settings '{...}'` or managed settings beat it (`hooks#disable-or-remove-hooks`, `settings-reference#disableallhooks`, `permissions#what-runs-before-you-trust-a-folder` last list). `--bare` skips hook discovery entirely (`headless#start-faster-with-bare-mode`). `--setting-sources` can drop the user layer. Managed `allowManagedHooksOnly` blocks user hooks (`hooks#hook-locations`).
- Provenance: Claude Code keeps no hash or trust record per hook; presence in the JSON is the whole registration.

Verdict (Claude Code): a user-scope hook can block *use* at three points, `UserPromptSubmit` (every turn, 30 s budget, fails open), `PreToolUse` (every tool call including `Skill`, MCP tools with server provenance, `Bash`, file tools; fails open on timeout) and `UserPromptExpansion` (the `/skill` path). It cannot block loading: `SessionStart` and `InstructionsLoaded` carry no decision, MCP servers are started before `SessionStart`, and settings helpers run before any hook. A repository can disable the gate with one settings key.

## 3. Codex

### 3.1 Events that fire before an Item is used

Twelve events exist (`codex-rs/config/src/hook_config.rs:35-61`). `prompt` and `agent` handlers are parsed and skipped; `command` and `mcp_tool` run (`codex-rs/hooks/src/engine/discovery.rs:635-654`). Default timeout is 600 s for every event except `SessionEnd` and `Interrupt` (1 s default, clamped to 1-3 s) (`discovery.rs:740-763`).

| Event | Fires | Can block? | What a block stops | On timeout | Source |
|---|---|---|---|---|---|
| `SessionStart` | Inside the first `run_turn` of the session (and again on `compact`); the source is queued at session configure and consumed once | Partly: JSON `continue: false` sets `should_stop`, `run_turn` returns `Ok(None)` and no model request is made. The queued source is popped before the hook runs, so the next prompt starts a normal turn. Exit 2 is not a block on this event | the first turn only | error, status `Failed`, turn continues | `codex-rs/hooks/src/events/session_start.rs:218-284`, `codex-rs/core/src/hook_runtime.rs:126-175`, `codex-rs/core/src/session/turn.rs:320-322` |
| `UserPromptSubmit` | Every turn, after skills/plugins are built and SessionStart hooks ran, before the injected skill bodies are recorded and before the first model request | Yes: `decision: "block"` + `reason`, or exit 2 with stderr. `run_turn` returns `Ok(None)`; the skill injection items are recorded only "after hooks accept the turn" | the whole turn, including the `$skill` bodies that were read for it | error, turn continues (fails open) | `codex-hooks-doc` UserPromptSubmit, `turn.rs:366-400`, `turn.rs:839-889` |
| `PreToolUse` | Before shell (`Bash`, incl. unified exec), `apply_patch` (aliases `Edit`/`Write`), MCP tools (`mcp__server__tool`), other local function tools (`spawn_agent` as `Agent`); not hosted tools such as `WebSearch`; "some specialized tool paths can opt out" | Yes: `hookSpecificOutput.permissionDecision: "deny"`, legacy `decision: "block"`, or exit 2 with a non-empty stderr (exit 2 with empty stderr is a `Failed` run and does not block). `ask`, `continue: false` are parsed, marked failed, and the call proceeds | that one tool call | `outcome: "timeout"` → `Failed` → call proceeds (fails open) | `codex-hooks-doc` PreToolUse and Tool coverage, `codex-rs/hooks/src/events/pre_tool_use.rs:205-275`, `codex-rs/hooks/src/engine/command_runner.rs:290-334` |
| `PermissionRequest` | Only when Codex is about to ask for approval (sandbox escalation, managed network); not for calls that need none | Yes: `hookSpecificOutput.decision.behavior: "deny"`; any deny wins over allows | that one approval | flow unchanged | `codex-hooks-doc` PermissionRequest |
| `PreCompact` / `PostCompact` | Around compaction | `continue: false` stops before / after compacting | compaction, not content | — | `codex-hooks-doc` |
| `SubagentStart` | A spawned subagent's first turn | No (`continue: false` parsed, ignored) | nothing | — | `session_start.rs:223-224` doc comment |
| `PostToolUse`, `Stop`, `SubagentStop`, `SessionEnd`, `Interrupt` | after the fact | not before use | — | — | `codex-hooks-doc` |

There is no Codex event for "instruction file loaded", "config changed", "skill catalogued" or "MCP server started". Matching hooks from every file run, and multiple handlers launch concurrently, "so one hook can't prevent another matching hook from starting" (`codex-hooks-doc` runtime notes). Background (`async: true`) hooks "can't block, approve, rewrite, or otherwise control the operation".

### 3.2 What the handler sees

Common stdin fields: `session_id`, `transcript_path`, `cwd`, `hook_event_name`, `model`, and on the events above `permission_mode` (`codex-hooks-doc` Common input fields; `codex-rs/hooks/src/events/session_start.rs:130-139` for the SessionStart payload). There is no project-root variable in the environment; `cwd` is the session cwd and the command "runs with the session `cwd` as its working directory". Plugin hooks additionally get `PLUGIN_ROOT`, `PLUGIN_DATA`, `CLAUDE_PLUGIN_ROOT`, `CLAUDE_PLUGIN_DATA` (`discovery.rs:262-270`).

| Event | Item-naming fields |
|---|---|
| `UserPromptSubmit` | `turn_id`, `prompt` |
| `PreToolUse` / `PostToolUse` | `turn_id`, `tool_name` (canonical: `Bash`, `apply_patch`, `mcp__<server>__<tool>`, function-tool name), `tool_use_id`, `tool_input` (`command` for Bash and apply_patch; the argument object for MCP and function tools). No MCP server provenance field is delivered; the server is only in the tool-name prefix |
| `PermissionRequest` | `turn_id`, `tool_name`, `tool_input` (+ optional `tool_input.description`) |

Skills in Codex are not invoked through a tool: the catalogue is injected as instructions and a `$mentioned` skill's body is loaded by `build_skills_and_plugins` at turn start (`turn.rs:308-318,1005-1142`), so the only hook that sits before a skill body reaches the model is `UserPromptSubmit`; a skill's `scripts/` are then ordinary shell calls seen by `PreToolUse` as `Bash` with the path in `tool_input.command`.

### 3.3 Where the hook must live, trust and hash pinning

- Location: `~/.codex/hooks.json` or inline `[hooks]` in `~/.codex/config.toml` (user layer). Hooks are discovered from every *enabled* config layer (`layers_low_to_high()` filters out disabled layers, `codex-rs/config/src/state.rs:548-551`); an untrusted project's `.codex` layer is disabled ("To load project-local config, hooks, and exec policies, add <path> as a trusted project", `codex-rs/config/src/loader/mod.rs:1082-1100`), but the user and system layers stay enabled, so a user-level hook fires in untrusted projects too ("In untrusted projects, Codex still loads user and system hooks", `codex-hooks-doc` Where Codex looks for hooks).
- Trust gate: every non-managed handler is listed, but only pushed to the runnable handlers when `enabled` and its `trust_status` is `Managed` or `Trusted`, or `--dangerously-bypass-hook-trust` was passed (`discovery.rs:713-734`). Status is `Trusted` when `[hooks.state."<key>"].trusted_hash` equals the current hash, `Modified` when it differs, `Untrusted` when absent (`discovery.rs:794-811`). This resolves the earlier unverified point in `codex-surfaces.md` section 6: an untrusted or modified hook is silently not run.
- Where trust lives: `hook_states_from_stack` reads `hooks.state` only from the `User` layer and session `-c` flags (`codex-rs/hooks/src/config_rules.rs:15-45`), so the pin must be in `~/.codex/config.toml`. The TUI writes it through `ConfigBatchWrite` on `hooks.state` with `{ "<key>": { "trusted_hash": "<hash>" } }` (`codex-rs/tui/src/hooks_rpc.rs:58-88`), the app server does the same per key (`codex-rs/app-server/src/effective_plugin_change.rs:88-95`). The interactive TUI runs a startup hooks review whenever a hook needs review (`codex-rs/tui/src/startup_hooks_review.rs:71-83`); in non-interactive `codex exec` nothing prompts and the hook simply does not run (only the discovery gate applies).
- Key format: `<key_source>:<event_snake_case>:<group_index>:<handler_index>`, with `key_source` = the hooks file path as displayed (`source_path.display()`) for file hooks, or `<plugin>@<marketplace>:hooks/hooks.json` for plugins (`codex-rs/hooks/src/lib.rs:113-123`, `discovery.rs:129-186`). Indices are positional: inserting a group ahead of an existing one renumbers that one and invalidates its pin, so AgentSweep must append.
- Hash algorithm (`discovery.rs:766-792`, `codex-rs/config/src/fingerprint.rs:54-66`): serialise the identity `{ event_name: "<snake_case>", matcher: <group matcher or omitted>, hooks: [ <normalised handler> ] }` to TOML (so `None` fields vanish), convert to JSON, sort object keys recursively, serialise compactly, SHA-256, prefix `sha256:`. The normalised command handler is `{ type: "command", command, timeout: <effective seconds, always present, default 600>, async, statusMessage?, additionalContextLimit? (omitted when equal to the 2500 default) }` with `commandWindows` dropped on non-Windows (`discovery.rs:505-566`, `hook_config.rs:161-185` for the serde names). AgentSweep can compute this and write the pin itself; the risk is version skew in the normalisation, which would leave the hook `Modified` and silently off.
- Kill switches: `[features] hooks = false` in any enabled layer, including a *trusted* project's `.codex/config.toml` (the project denylist does not cover `features`, `codex-surfaces.md` section 1.1); `[hooks.state."<key>"] enabled = false` (user layer only); `allow_managed_hooks_only` in `requirements.toml`. The feature is `Stage::Stable, default_enabled: true` at HEAD (`codex-rs/features/src/lib.rs:1210-1215`).

Verdict (Codex): a user-level hook can block *use* at `UserPromptSubmit` (every turn, before skill bodies are recorded) and `PreToolUse` (shell, `apply_patch`, MCP and function tools; fails open on timeout), and can end the very first turn from `SessionStart`. It cannot block loading: AGENTS.md, the skill catalogue, plugins and the MCP runtime are in place before the first hook, and `SessionStart` itself runs only when the first turn begins. The hook runs in untrusted projects, but only after its hash is trusted in the user `config.toml`, which AgentSweep must either compute and write or leave to the TUI review.

## 4. AgentSweep's own hook entry under its Drift rules (ticket 18)

- The hook entry is a user-scope Hook Item in both Agents (`~/.claude/settings.json#UserPromptSubmit/…`, `~/.codex/hooks.json#user_prompt_submit/…`), located by `<file>#<event>/<matcher>/<12 hex of the normalised handler hash>` (ticket 18, round 1 item 1; the normal form is Codex's `{event_name, matcher, hooks:[handler]}`, the same identity Codex hashes in `discovery.rs:775-792`).
- User-scope active Hook Items raise a visible Drift Finding on `added` or `changed` unless a known action stands behind the change (ticket 18, round 1 items 5-6). AgentSweep's own write is a known action, so registering the hook moves the Baseline forward and raises nothing. The `[hooks.state]` entry AgentSweep writes in `~/.codex/config.toml` is the same case (a known action) and ticket 18 already lists `[hooks.state]` among the entries that never raise Drift.
- The rules then protect the gate: if an attacker edits the command, the locator changes, the Item is `added` and the old one gone in the same Scan, shown as "replaced"; if the entry is deleted, the Hook Item disappears (disappearance is never a Finding, ticket 18 item 10) but the daemon can notice its own registration is missing on the next Full Scan and re-register or report Protection degraded. That check is not part of the Drift rules and needs its own place in the scan lifecycle.
- The Agent-side kill switches (`disableAllHooks: true` in a project `.claude/settings.json`, `[features] hooks = false` in a trusted `.codex/config.toml`, `[hooks.state."<AgentSweep key>"] enabled = false`) are the attacker's cheaper move and are Project or User scope SettingsEntry Items: a Rule for each is the natural companion of the toggle, since without it the gate can be switched off without any Finding.

## 5. The handler under the ticket 13 process model

- Command: the in-bundle `agentsweep` CLI, in Claude Code exec form (`"command": "/path/to/agentsweep", "args": ["gate", "--agent", "claude-code"]`, no shell, placeholders substituted as plain strings) and in Codex as a plain `command` string (Codex has no exec form; the string goes through the shell). Both Agents hand the event JSON on stdin and read JSON from stdout. The CLI is a signed peer, so it may ask the daemon (ADR 0008).
- Request: the hook knows the project only as `cwd` (plus `CLAUDE_PROJECT_DIR` in Claude Code). The daemon's request vocabulary takes a path only for Folder Scan and reveal-Receipt (ADR 0008), so a gate needs one new request that carries `cwd` and returns a closed verdict (`clear`, `block` with a one-line reason and a Finding count, or `unknown`), never Finding text or Item paths. The daemon resolves `cwd` against the pooled project roots and answers from the open Findings it already keeps by Item id (`state.json`). At `PreToolUse` the CLI can also pass the tool name and the Item-naming fields (`tool_input.skill`, `mcp_server.name`/`source`, `tool_input.file_path`, the `Bash` command) so the daemon can match the call to an open Threat Finding on that Item; the daemon still returns only a verdict.
- Fixed fallback: daemon unreachable means Protection is off (ticket 13, health), and both Agents already fail open when a hook times out. Failing closed would lock every Agent session on the machine whenever the daemon is not running, including after Uninstall if the entry outlived the app. Recommended fixed fallback: allow, with `systemMessage: "AgentSweep is not running; nothing was checked"` so the user sees it once per turn. The CLI needs its own connect-and-read deadline (about 2 s) well under the hook `timeout`, which must be set explicitly in the entry (recommended 5 s): Claude Code's default on `UserPromptSubmit` is 30 s, Codex's is 600 s, and a hung daemon would otherwise stall every prompt for that long.
- What to block: `UserPromptSubmit` while any open Threat Finding exists on the project's Items or on User-scope Items (a session gate that fires before the model sees the prompt and, in Codex, before the mentioned skill bodies are recorded); `PreToolUse` on `Skill` (Claude Code) and on `mcp__<server>__.*` and `Bash` (both) when the call names an Item with an open Threat Finding. Exposure Findings and Ambiguous Band never block, in line with the glossary (only Threat may act automatically).
- Registration: written by the daemon (single writer) as one hook group appended per event in the user files; for Codex also the `[hooks.state]` pin, computed as in section 3.3, and a note in Settings that Codex will ask to review the hook once if the pin does not match. Removal on Uninstall through the same path.

## 6. Conclusion

Feasible in v1 as a Settings toggle, but as a **use-time gate**, not load-time interception, and it should be named that way in the UI. The deciding facts:

1. No hook event in either Agent fires before instruction files, skill catalogues, plugins, settings helpers or MCP server processes are loaded; Claude Code's `SessionStart` and `InstructionsLoaded` cannot block, Codex's `SessionStart` runs inside the first turn and can only end that turn. Quarantine therefore stays the only load-time defence.
2. Both Agents let a user-scope command hook block every turn at `UserPromptSubmit` and every tool call at `PreToolUse`, with the project identified through `cwd` and the Item through `tool_input` (`Skill` name, `mcp__server__tool` plus, in Claude Code, `mcp_server.source`, file paths, shell commands). That is enough to stop a flagged skill, MCP tool or script from being *used* between the Scan that flagged it and the user's reaction.
3. Both fail open on timeout and both can be switched off by a repository the user opens (`disableAllHooks` in project settings; `[features] hooks = false` in a trusted `.codex/config.toml`) or by launch flags (`--bare`, `--settings`, `--setting-sources`, `--dangerously-bypass-hook-trust` does the opposite). The toggle is defence in depth, never the primary control.
4. Codex runs a user hook only after its normalised hash is pinned under `[hooks.state]` in the user `config.toml`; AgentSweep can write the pin itself (algorithm in section 3.3) or accept a one-time TUI review; in `codex exec` an unpinned hook is silently skipped.
5. The handler fits ADR 0008 with one new closed IPC request (`gate`, takes `cwd`, returns a verdict) and a fixed allow-with-message fallback when the daemon is unreachable.

## 7. Unverified points

- Claude Code `SessionStart` and the universal `continue: false`: the reference says every event accepts the field and lists the events that discard it; `SessionStart` is on neither list, and the decision-control table's "No blocking or decision control" row for it does not name the universal fields. Verify by running a `SessionStart` hook that prints `{"continue": false, "stopReason": "x"}` and observing whether the first prompt is processed. Even if honoured, it would end processing after loading, not before.
- Claude Code `Skill` tool `tool_input` keys (`skill`, `args`) are taken from the tool schema of the running binary (2.1.273), not from the hooks reference, which lists no schema for `Skill`. Verify with a `PreToolUse` hook matching `Skill` that logs stdin.
- Whether `UserPromptExpansion` blocking runs before or after a skill's `` !`cmd` `` inline commands execute. The skills doc says those run "before content is sent"; the ordering against the hook is not documented. Verify with a skill whose inline command touches a file and a hook that blocks its expansion.
- Whether Claude Code fires `SessionStart` before or after the interactive workspace-trust dialog in a never-trusted folder (the docs say hooks are held back until acceptance, not where in the startup sequence the dialog sits).
- Codex: the exact call that spawns stdio MCP server processes. `McpStartupPolicy::Eager` is selected for main sessions and the MCP runtime is installed at session configure before the SessionStart source is queued (`session.rs:1854-1893`, `mcp_runtime.rs:358-362`), but the spawn site inside the MCP runtime crate was not read.
- Codex `SessionStart` on `resume`: the doc lists `resume` among matcher values and the source queues `Resume`; whether `continue: false` on resume behaves as on startup was not traced beyond the shared code path.
- The Codex hash reproduction in section 3.3 is derived from reading the serde attributes and the normaliser, not by computing a hash and comparing it with one Codex wrote. Verify by writing a test hook, letting `/hooks` trust it, and comparing the stored `trusted_hash` with an AgentSweep-computed one.
- Whether Codex's `codex exec` (non-interactive) surfaces any warning for a skipped untrusted hook; only the TUI review path was read.
