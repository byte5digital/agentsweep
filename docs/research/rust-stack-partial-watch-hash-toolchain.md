# File watching, hashing and toolchain (PARTIAL, subagent findings, 2026-09-16)

Provenance: sub-report of the Rust stack research ticket, produced before the session rate limit. Fold into docs/research/rust-stack.md.

## notify
- Stable 8.2.0 (2025-08-03), MSRV 1.77, uses fsevent-sys. Pre-release 9.0.0-rc.5 (2026-08-30), MSRV 1.88, objc2 bindings, `Config::with_fsevent_latency`, `watch_with` per-path settings, `watched_paths`, `update_paths`, tokio/futures handlers, `EventKindMask` filtering. 9.0 has been in RC for 8 months. Policy: N-2 stable Rust supported, MSRV may bump in minors. Active maintenance (commits 2026-09-14). CC0-1.0. https://crates.io/api/v1/crates/notify , https://raw.githubusercontent.com/notify-rs/notify/main/notify/CHANGELOG.md
- Backends: Linux inotify; macOS FSEvents (default) or kqueue (`macos_kqueue` feature); Windows ReadDirectoryChangesW; BSD kqueue; PollWatcher everywhere. https://raw.githubusercontent.com/notify-rs/notify/main/README.md
- Recursion: FSEvents and Windows native; inotify and kqueue emulated by walking the tree and adding per-directory (inotify) or per-file (kqueue) watches, with a documented race for files created before the new watch exists. https://man7.org/linux/man-pages/man7/inotify.7.html
- Limits: inotify `max_user_watches` default 1% of RAM clamped to [8192, 1048576], ENOSPC mapped to `ErrorKind::MaxFilesWatch`, queue overflow becomes `Flag::Rescan`; kqueue is fd-per-file (issue #596: 300 files hits "Too many open files" at ulimit 256, recommendation: use FSEvents); Windows 16 KB buffer, overflow becomes `Flag::Rescan`; FSEvents `KernelDropped`/`UserDropped` require a full scan and notify maps `MustScanSubDirs` to `Rescan`. Issue #412: ~16% of 1500 individually watched files never fired on any OS (upstream wontfix). https://docs.rs/notify/9.0.0-rc.5/notify/ , https://github.com/notify-rs/notify/issues/596 , https://github.com/notify-rs/notify/issues/412
- Design implication: every backend can emit `Flag::Rescan`; the daemon needs a full-rescan path and must not assume event completeness. This also justifies the daily scheduled full scan.
- FSEvents semantics: notify passes `FileEvents | NoDefer | WatchRoot`, so file-level paths are delivered; default latency zero; `sinceWhen = SinceNow`, so no historic event replay and no catch-up API after daemon downtime (scan yourself). notify spawns its own CFRunLoop thread; no run-loop plumbing needed. https://developer.apple.com/library/archive/documentation/Darwin/Conceptual/FSEvents_ProgGuide/UsingtheFSEventsFramework/UsingtheFSEventsFramework.html
- Gotchas: atomic-save editors produce create-and-replace or truncate patterns; APFS copy-on-write fires metadata events on the source path; symlinks followed by default; renames paired by cookie on inotify, unpaired on kqueue.
- notify-debouncer-full 0.7.0 stable (2026-01-23) / 0.8.0-rc.2 pairs with notify 9. Stitches renames, dedupes creates, drops modify-after-create. `new_debouncer(timeout, tick_rate, handler)`. On macOS/Windows the default `FileIdMap` cache stats and stores one entry per file in the watched tree at watch time (memory caveat inferred from source); `NoCache` opt-out loses rename stitching. https://raw.githubusercontent.com/notify-rs/notify/main/notify-debouncer-full/src/lib.rs
- macOS TCC: Desktop, Documents and Downloads prompt on first access (`NS*FolderUsageDescription` keys). A headless launchd agent has no UI to prompt from, so watching those folders from the daemon will silently fail unless access was granted. Whether `~/Library/Application Support` is exempt is unverified. The agent config dirs (`~/.claude`, `~/.codex`) are in the home root, not TCC-protected folders. https://developer.apple.com/documentation/bundleresources/information-property-list/nsdesktopfolderusagedescription

## Hashing
- blake3 1.8.7 (2026-08-20), CC0/Apache-2.0, no official MSRV (CI 1.85.1), edition 2024; NEON assumed on aarch64; `update_reader`, `update_mmap`, `update_mmap_rayon`; `update_rayon` slower under 128 KiB. Specified in C2SP, not NIST. https://crates.io/api/v1/crates/blake3 , https://docs.rs/blake3/latest/blake3/struct.Hasher.html
- sha2 0.11.0 (2026-03-25), MSRV 1.85, edition 2024; asm features removed; SHA-256 hardware accelerated by default via runtime detection on Apple Silicon and SHA-NI x86; depends on digest 0.11 while much of the ecosystem still pins 0.10 (duplicate crates likely). https://raw.githubusercontent.com/RustCrypto/hashes/master/sha2/README.md
- Recommendation supported by sources: SHA-256 for Trust and Allowlist hashes (external lookups and `shasum -a 256` verification), BLAKE3 optionally for internal change detection. Numeric throughput figures unverified.
- Gotcha: mmap hashing of a file being truncated by another process can SIGBUS (relevant when agents write files concurrently); not confirmed as a documented warning.

## Rust toolchain
- Stable 1.98.1 (2026-09-03, miscompilation fix); 1.99.0 due 2026-10-01. Edition 2024 default for `cargo new` since 1.85 (2025-02-20). All surveyed MSRVs (notify 1.77/1.88, blake3 ~1.85, sha2 1.85, yara-x 1.93) satisfied. Pin `rust-version` in the workspace and expect bumps every few months if tracking notify 9.x. https://blog.rust-lang.org/2026/09/03/Rust-1.98.1/ , https://releases.rs/

## Unverified
Apple limit on FSEvents stream paths; TCC status of `~/Library/Application Support`; numeric hash throughput; VirusTotal SHA-256 keying; debouncer memory caveat as documented; blake3 mmap SIGBUS warning; distro overrides of inotify limits.
