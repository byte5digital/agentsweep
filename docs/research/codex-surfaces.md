# Codex CLI surface inventory

Answers `.scratch/ai-antivirus/issues/02-codex-surfaces.md`. Scope: the on-disk Surfaces (see `CONTEXT.md`) that OpenAI Codex CLI reads instructions or executable configuration from, as a Surface Adapter would need to know them.

Verified against (2026-09-16):

- Source: `openai/codex` at commit `8f38d5a877da8c5c2c0b5158e72bb5f2290a3157` (main, 2026-09-16), sparse-checked-out to the scratchpad. Cited as `codex-rs/<path>`. The repo's `docs/*.md` are now 3-line stubs that link to the hosted docs, so source code is the authoritative primary source for behaviour.
- Hosted docs: `developers.openai.com/codex/*` now 308-redirects to `learn.chatgpt.com/docs/*`; both URLs are cited where used.
- Live machine: `codex-cli 0.144.5` (`~/.local/bin/codex`), `~/.codex/` tree, and `~/Developer/vismed/.codex/`. Structure and keys only; `~/.codex/auth.json` was never opened; nothing secret-looking was found in the files that were read.

Layer ordering shorthand used below (lowest to highest precedence): `package < mdm < system < cloud < user < profile < project(root..cwd) < session flags`, with legacy `managed_config.toml` above session flags. Source: `codex-rs/config/src/loader/README.md` and the doc comment at `codex-rs/config/src/loader/mod.rs:99-131`.

## 2. Project discovery and trust registry

1. Project root: nearest ancestor of cwd containing a marker from `project_root_markers` (default list; `.git` is one). Git repo root and, for linked worktrees, the main repository root are also computed (`resolve_root_git_project_for_trust`). Source: `loader/mod.rs:1248-1262`, `codex-rs/core/src/agents_md.rs:10-18`.
2. Trust registry: `[projects."<absolute path>"] trust_level = "trusted" | "untrusted"` in the user `config.toml` (also settable by system, MDM, cloud and legacy managed layers, which take part in the trust decision at their normal precedence). Lookup order for each `.codex` dir: the directory itself, then the project root, then the git repo root; first hit wins. No entry means untrusted. `TrustLevel` enum is exactly `Trusted | Untrusted`. Source: `loader/mod.rs:1010-1064`, `codex-rs/protocol/src/config_types.rs:640-645`.
3. What trust gates: project `config.toml` values, project `hooks.json`/`[hooks]`, project `rules/`. Explicitly not gated by trust in the code read: `AGENTS.md`, `.agents/skills`. `.codex/skills` from a disabled layer: unverified.
4. Even when trusted, the project layer denylist (section 1.1) blocks provider, auth, notify, profile and telemetry keys, with a startup warning listing what was dropped.
5. Parse failure in a trusted project `config.toml` aborts startup with "Error parsing project config file …"; in an untrusted project the broken file is replaced by an empty layer and startup continues. Source: `loader/mod.rs:1660-1685`.
6. Live: eight trusted paths are registered, including `~/Developer/vismed` (so its `.codex/config.toml` MCP servers are active) and `~/Library/Application Support/com.conductor.app/bin` and `~/conductor/repos/Quickstart` (third-party "conductor" app directories).

## 3. Plugin and skill lifecycle

- System skills: on every host skills service start `install_system_skills` compares `$CODEX_HOME/skills/.system/.codex-system-skills.marker` with the fingerprint of the embedded samples and rewrites the whole `.system/` directory when it differs. Anything a user or attacker places under `.system/` is therefore ephemeral. Source: `codex-rs/skills/src/lib.rs:77-99`, `ext/skills/src/host_service.rs:413`.
- User skills: created by hand, by `skill-creator`, or by `skill-installer` (curl/git from `github.com/openai/skills` or any repo path, including private ones) into `$CODEX_HOME/skills/<name>/`. No hash, signature or registry file is written; presence on disk is the whole install. Source: live `~/.codex/skills/.system/skill-installer/SKILL.md`.
- Repo skills: committed to `.agents/skills/` or `.codex/skills/`; loaded on session start for any cwd inside the tree.
- Plugins: `codex plugin marketplace add <git|path>` writes `[marketplaces.<name>]` to user `config.toml` and clones to `.tmp/marketplaces/<name>/`; installing writes the plugin tree to `plugins/cache/<marketplace>/<plugin>/<version>/` and `[plugins."<plugin>@<marketplace>"] enabled = true`. Remote-catalog plugins are staged in `plugins/.remote-plugin-install-staging/` then moved under `openai-curated-remote/` with a `.codex-remote-plugin-install.json`. The curated `openai/plugins` repo is git-synced at startup into `.tmp/plugins/` (`startup_sync.rs`). Disable with `enabled = false`; uninstall via `/plugins` or CLI (`codex plugin` subcommands; exact uninstall verb unverified).
- Plugin hooks enter the same trust flow as user hooks; the five warp hooks on this machine were trusted (hashes persisted) on 2026-07-15.
- Nothing in the lifecycle verifies content integrity after install: marketplace git checkouts are pinned by revision in `config.toml`, but the extracted `plugins/cache` copy and `$CODEX_HOME/skills` are plain directories with no manifest of hashes. This is the gap a Trust-by-hash Allowlist (T0) would fill.

## 5. Native blocklist / disable mechanisms (for Quarantine design)

- Per item `enabled = false`: MCP servers (`mcp_servers.<id>.enabled`, plus `enabled_tools`/`disabled_tools`), plugins (`plugins."<id>".enabled`), plugin MCP servers, apps (`apps.<id>.enabled`, `tools.<t>.enabled`), skills (`[[skills.config]] path|name, enabled = false`), hooks (`[hooks.state."<key>"] enabled = false`), bundled skills (`skills.bundled.enabled`).
- Feature kill switches: `[features] hooks = false`, `remote_plugin = false`, `apps = false`, `multi_agent = false`, `memories = false`.
- Trust: removing `[projects."…"]` or setting `trust_level = "untrusted"` disables a whole project's `.codex` config, hooks and rules in one move.
- Admin only: `requirements.toml` (`/etc/codex/requirements.toml`, MDM, cloud) can force `allow_managed_hooks_only`, sandbox and approval constraints, and enforced rules; `config.toml` cannot.
- Exec policy `decision = "forbidden"` can block command prefixes (a natural home for a scanner-written deny rule, but note the strictest-wins merge only helps if the rule file itself is loaded).
- There is no native allowlist by content hash, no signature check on skills or plugins, and no per-file quarantine. All disable mechanisms are config-key based, so a Quarantine that moves files out of the Surface is complementary rather than duplicative.

- Whether `~/.codex/hooks.json` hooks without a `[hooks.state]` entry run, are prompted for, or are silently skipped (only the trust-status enum was read, not the runtime gate).
- Whether `.codex/skills` from an untrusted (disabled) project layer is loaded.
- Exact fallback when a `.rules` file fails to parse (warning observed; resulting policy not traced).
- `SKILL.json` as an alternative to `SKILL.md` frontmatter (mentioned in a protocol doc-comment only).
- `codex plugin` uninstall verb and the CLI flag name behind `ignore_user_and_project_exec_policy_rules`.
- Purpose of `~/.codex/tmp/arg0/` and whether `shell_snapshots/*.sh` are integrity-checked before sourcing.
